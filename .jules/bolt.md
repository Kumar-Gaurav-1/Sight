## 2024-05-24 - Cached DateFormatter requires strict thread safety consideration in Swift 6
**Learning:** `DateFormatter` is heavily created repeatedly (e.g. in `MenuBarViewModel`, `AdherenceManager`, `Preferences`). Recreating `DateFormatter` is very expensive and is a known performance issue. Creating a singleton cache solves this, but due to Swift 6 strict concurrency checks, sharing mutable singletons or static properties causes `@MainActor` or isolation warnings if not configured as `@unchecked Sendable` wrapper where all properties are standard `let` initialized synchronously. Moreover, `ISO8601DateFormatter` timezone should *never* be altered to `.autoupdatingCurrent`, it must remain as Z/UTC, unlike normal `DateFormatter`.
**Action:** When globally caching `DateFormatter` in Swift 6, create a `final class Formatters: @unchecked Sendable` with all properties defined as `let`. Setup individual formatters (short time, EEE, EEEE, h a, yyyy-MM-dd) using a private initializer or static let closures. Ensure ISO8601 keeps its default timezone, while others get `.autoupdatingCurrent` locale/timezone if applicable.
