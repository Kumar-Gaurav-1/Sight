## 2026-11-02 - Fixing Strict Concurrency Syntax Errors in CI
**Learning:** In Swift 6 strict concurrency, indiscriminately applying `@MainActor` to simple static UI properties (e.g., `Color`, `LinearGradient`) inside centralized theme structs or enums causes pervasive 'main actor-isolated static property can not be referenced from a non-isolated context' compilation errors across all non-isolated SwiftUI views and initializers referencing them. Additionally, older Swift compilers used in CI environments will fail with 'expected var keyword in property declaration' when they encounter `nonisolated(unsafe)`.
**Action:** Leave foundational UI types like `Color` unannotated, as they are inherently `Sendable`. For singletons or static properties using `nonisolated(unsafe)`, wrap the declaration in `#if compiler(>=5.10)` blocks with an `#else` fallback matching the original declaration (e.g., standard `public static var`) to ensure backward compatibility.

## 2026-11-02 - Memory Leaks and Strict Concurrency in Swift 6
**Learning:** In Swift 6 strict concurrency, when dispatching work to a nested `Task { @MainActor in }` from within an outer closure that captures `[weak self]` (like Combine `.sink` or `Timer`), do NOT replace the outer `[weak self]` with `[self]` as this causes severe memory leaks. Additionally, standard `Task { @MainActor in }` closures complain about referencing captured variables (like `self`) in concurrently-executing code. Finally, `Foundation.Notification` does not conform to the `Sendable` protocol, so it cannot be captured in a `@Sendable` closure like a Task.
**Action:** Safely unwrap `self` outside the task (`guard let self = self else { return }`), and then explicitly capture the unwrapped strong reference in the Task's capture list (`Task { @MainActor [self] in }`). Extract any non-sendable properties (like data from `notification.userInfo`) synchronously outside the Task and pass only the extracted, sendable primitive values into the concurrent context.

## 2026-11-02 - Testing @MainActor Isolated Classes
**Learning:** In Swift 6 strict concurrency, if an `ObservableObject` class like `TimerStateMachine` is heavily isolated to the `@MainActor` to ensure thread-safe UI updates, the `XCTestCase` suite testing it will fail to compile. Test methods run synchronously and non-isolated by default, leading to errors like 'call to main actor-isolated instance method in a synchronous nonisolated context' or 'main actor-isolated property can not be referenced from a non-isolated autoclosure'.
**Action:** Annotate the entire `XCTestCase` subclass (e.g., `@MainActor final class TimerStateMachineTests: XCTestCase`) to ensure `setUp()`, `tearDown()`, and all test methods correctly run on the MainActor, satisfying strict concurrency checks when accessing isolated test subjects.
