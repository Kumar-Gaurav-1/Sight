## 2024-05-14 - Global DateFormatter Caching in Swift 6
**Learning:** `DateFormatter` instantiations are computationally expensive and cause UI hitching/overhead when run frequently in SwiftUI views or loops. A common optimization is to create a globally shared static instance. However, Swift 6's strict concurrency model prevents nonisolated concurrent access to static properties. To safely bypass this without forcing main actor isolation (which breaks background thread parsing in data exports), we must wrap the static formatters in a `@unchecked Sendable` singleton. Additionally, we must use `let` values (no `lazy var`) during its synchronous `init` to guarantee thread safety. ISO8601DateFormatter specifically must not inherit `.autoupdatingCurrent` timezone to prevent timestamp corruption.
**Action:** Create a `SharedFormatters` singleton class explicitly marked `@unchecked Sendable` with standard `let` initializations. In the replacement scripts, ensure the exact target text replacements are used without assuming file structure. When addressing `expected var keyword in property declaration` syntax errors on older Swift environments in CI, wrap the `@unchecked Sendable` declaration block in an `#if compiler(>=5.10)` check with a safe standard `var` fallback `#else` branch.
## 2024-05-14 - Fixing Strict Concurrency Syntax Errors in Swift 6
**Learning:** In Swift 6 strict concurrency, if standard SwiftUI `View` structs trigger 'main actor-isolated property can not be referenced from a non-isolated context' errors, explicitly annotate the entire struct definition with `@MainActor`. Additionally, if a custom SwiftUI `ViewModifier` accesses `@MainActor`-isolated state or methods, the struct itself must be annotated with `@MainActor`. Furthermore, any `View` extension methods applying that modifier must also be explicitly annotated with `@MainActor` to prevent 'call to main actor-isolated initializer' compiler errors.
**Action:** When fixing actor isolation errors in a SwiftUI file containing multiple view structs (e.g., helper views or subcomponents), ensure `@MainActor` is applied to all relevant view structs within the file, not just the primary view, to completely resolve cross-referencing isolation warnings. For `ButtonStyle` and `ToggleStyle`, extract `@MainActor`-isolated properties into a separate View or remove the isolated state. If Swift older versions complain about `expected 'var' keyword` when using `nonisolated(unsafe) public static var`, wrap the declaration in an `#if compiler(>=5.10)` block. Do not indiscriminately apply `@MainActor` to simple static UI properties (e.g., `Color`, `LinearGradient`) inside centralized theme structs or enums, as these foundational UI types are inherently `Sendable` and adding `@MainActor` needlessly isolates them, triggering pervasive compilation errors.
## 2024-05-14 - Fixing Strict Concurrency Closures and Optionals in Swift 6
**Learning:** In Swift 6 strict concurrency, `Foundation.Notification` does not conform to `Sendable`. Passing a non-sendable type from a `@Sendable` closure into a detached `Task { @MainActor in }` causes a compiler error. Similarly, capturing `[weak self]` in an outer block (like `Timer` or `NotificationCenter`) and then conditionally unwrapping `self` inside a nested `Task { @MainActor in }` frequently triggers 'reference to captured var 'self' in concurrently-executing code' if the compiler cannot guarantee the `weak` reference won't change concurrently.
**Action:** When working with Notifications and Tasks, synchronously extract the needed primitive values (like `Int` from `userInfo`) *outside* the Task, and only pass those Sendable primitives into the Task block. For nested Tasks inside closures that capture `[weak self]`, safely unwrap `self` outside the task (`guard let self = self else { return }`) and explicitly capture the unwrapped strong reference in the Task's capture list (`Task { @MainActor [self] in }`).
## 2024-05-14 - Fixing Strict Concurrency Errors in XCTest
**Learning:** In Swift 6 strict concurrency, if an `ObservableObject` or global singleton being tested uses `@MainActor` properties, the `XCTestCase` suite testing it will fail with synchronous nonisolated context errors.
**Action:** Annotate the entire `XCTestCase` subclass (e.g., `@MainActor final class TimerStateMachineTests: XCTestCase`) to ensure `setUp()`, `tearDown()`, and all test methods run on the MainActor, allowing synchronous access to isolated properties.
